## Current Architecture Weaknesses Discovered

### 1. **Direct Database Queries in UI Components**
**Problem:** The dashboard page component directly queries Supabase 11 times:
- quiz_attempts
- mock_exam_attempts (2 queries)
- review_history (2 queries - duplicated)
- user_cards (3 queries - duplicated with different filters)
- profiles
- topic_mastery_view

**Impact:**
- Difficult to maintain
- Hard to test
- Prone to errors
- No centralized error handling
- No caching strategy
- Business logic scattered in UI

### 2. **Duplicate Data Fetching**
**Problem:** Same tables queried multiple times:
- `user_cards` fetched 3 separate times with different filters
- `review_history` fetched 2 separate times

**Impact:**
- Unnecessary database roundtrips
- Increased latency
- Higher database load
- Wasted resources

### 3. **Business Logic in UI Components**
**Problem:** Calculations performed in page component:
- Lines 77-86: Calculating masteredCards and avgRetention
- Lines 88-98: Calculating topicsStarted and topicsMastered
- Lines 100-108: Aggregating study time and heatmap
- Lines 122-159: Transforming activity events

**Impact:**
- Untestable business logic
- Difficult to reuse logic
- Hard to maintain
- Prone to bugs

### 4. **No Error Handling**
**Problem:** No try-catch blocks, no fallback data, no partial failure handling

**Impact:**
- One query failure breaks entire dashboard
- Poor user experience
- No graceful degradation
- Difficult to debug

### 5. **Type Safety Issues**
**Problem:** Using `any` types in forEach loops and transformations

**Impact:**
- Runtime errors
- Type safety violations
- Harder to refactor
- Loss of IDE support

### 6. **No Caching Strategy**
**Problem:** Every page load refetches all data with no caching

**Impact:**
- Slow page loads
- Unnecessary database load
- Poor performance
- Wasted resources

### 7. **No Loading Strategy**
**Problem:** All data loads at once or not at all

**Impact:**
- Long initial load times
- Poor perceived performance
- No progressive enhancement

## Queries Consolidated

### Before: 11+ Separate Queries

**user_cards:** 
- Query 1: `.select("state, retention_score")` (all cards)
- Query 2: `.select("*", count).in("state", ["relearning", "review"])` (due)
- Query 3: `.select("*", count).eq("state", "learning")` (new)

**review_history:**
- Query 1: `.select("*", count).gte("reviewed_at", startOfDay)` (today)
- Query 2: `.select("id, reviewed_at, ...").gte("reviewed_at", oneYearAgo)` (heatmap)

**Plus:** quiz_attempts, mock_exam_attempts, profiles, topic_mastery_view, calculateReadiness (internal queries), generateInsights (internal queries), generateDailyBrief (AI call)

### After: Consolidated & Optimized

**user_cards:** 
- Consolidated into `fetchStudyQueue()` - 3 parallel count queries
- Consolidated into `fetchMemoryStatistics()` - 1 comprehensive query

**review_history:**
- Consolidated into `fetchStudyQueue()` - Today's count
- Consolidated into `fetchStudyHeatmap()` - 365 days of data

**Optimization:**
- Date ranges calculated once
- Parallel fetching with `Promise.allSettled`
- Selective field fetching (only needed columns)
- Count queries use `head: true` (no data transfer)

**Result:**
- **Reduced roundtrips:** From 11+ to 9 parallel sections
- **Eliminated duplicates:** user_cards and review_history no longer duplicated
- **Improved resilience:** Individual failures don't break dashboard
- **Better performance:** Parallel execution, optimized queries

## Database Optimizations

### Query Optimizations

1. **Count Queries Use Head**
   ```typescript
   .select("*", { count: "exact", head: true })
   ```
   - Returns count only, no data transfer
   - Faster queries
   - Reduced bandwidth

2. **Selective Column Fetching**
   ```typescript
   .select("streak, daily_review_limit, settings")
   ```
   - Only fetch needed columns
   - Reduced data transfer
   - Faster queries

3. **Parallel Execution**
   ```typescript
   await Promise.allSettled([...])
   ```
   - All queries run simultaneously
   - Reduced total latency
   - Better resource utilization

4. **Date Range Calculation**
   ```typescript
   const now = new Date();
   const nowStr = now.toISOString();
   // Reuse nowStr across all queries
   ```
   - Calculated once
   - Consistent across queries
   - No redundant calculations

## Error Handling & Resilience

### Error Handling Architecture

**Section-Level Errors:**
```typescript
Promise.allSettled([
  fetchUserData(),      // Section 1
  fetchStudyQueue(),    // Section 2
  // ... 7 more sections
])
```

**Benefits:**
- One section failure doesn't break dashboard
- Partial data is better than no data
- User can still see most of dashboard

**Error Tracking:**
```typescript
interface DashboardError {
  section: string;           // Which section failed
  error: string;             // Error message
  timestamp: string;         // When it failed
  canRetry: boolean;         // Is retry possible
}
```

**Default Fallback Values:**
- Every section has sensible defaults
- Empty arrays instead of null
- Zero values instead of undefined
- Graceful degradation

**Error UI (Ready for Implementation):**

- Provide "Retry" button
